### Preserve historical snapshots on one Supabase project

The preferred hosting design keeps a small SQL catalog in the default `postgres` database and one read-only published database per snapshot on the same cluster. This retains the local version boundaries and the SQL methodology shipped in each dump. Supabase documents that PostgreSQL can contain additional databases and explains that its Dashboard and integrated tools center on the default database. Custom database connections and restoration are deployment acceptance checks. [Supabase multiple-database guidance](https://supabase.com/kb/troubleshooting/manually-created-databases-are-not-visible-in-the-supabase-dashboard-4415aa) · [Supavisor FAQ](https://supabase.com/kb/troubleshooting/supavisor-faq-YyP5tI)

- The authenticated publisher restores a candidate database, verifies the source hashes, row counts, release checks, and read-only grants, and retains its immutable manifest and dump in private Cloud Storage. It then advances the SQL catalog in one transaction. A failed or interrupted refresh leaves the previous version active. Each archived selection resolves to its own immutable database and methodology. [Local publication and restore](local_dataset_publication.md)
- Keep verified logical dumps for the catalog and every published database outside Supabase's database failure boundary. On Free, use these dumps for recovery. Pro adds managed daily backups. Before release, restore one archived version and the current version using the actual Cloud Run connection and compare cutoff behavior, lineage, and CSV contents with local results. If the chosen plan or pooler cannot serve the additional databases with the required permissions and backup strategy, hold the hosted release and review a single-database versioned-schema design. [Supabase backup guidance](https://supabase.com/docs/guides/platform/backups)

## Budget controls and release gates

- Confirm that the app is for personal, non-commercial portfolio use and that the personal GitHub repository can be connected under the owner's Hobby account. Confirm regional availability, billing currency, taxes, and checkout price before activating subscriptions. Set the initial Google Cloud project budget to **$5 per month** with alerts at 50%, 80%, and 100%. Confirm whether a separate Cloud Run spend cap is available for the billing account and test what it pauses. The project budget is an alert threshold. Cloud Run service caps have their own scope and timing, and other services can continue to accrue charges. [Vercel fair use](https://vercel.com/docs/limits/fair-use-guidelines) · [Google Cloud budgets](https://docs.cloud.google.com/billing/docs/how-to/budgets) · [Google Cloud spend caps](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)
- Keep Supabase Pro's Spend Cap enabled where supported. Review charge categories excluded from it and the recurring subscription separately. Keep the initial runtime limits, monitor all three bills, and ask for approval before increasing compute, adding a paid project, or changing tiers. Reprice the plan if the security review requires a public load balancer or dedicated outbound IP. [Supabase Spend Cap](https://supabase.com/docs/guides/platform/spend-cap)
- Record the owner's tier and spend approval before provisioning. Then use the first authorized hosted trial to validate database access, immutable snapshot restoration, artifact integrity, warm and cold behavior, and measured billing. The v1.2 warm target remains p95 under two seconds under stated low load. An open issue with cost, data access, or snapshot replay keeps public release pending.
